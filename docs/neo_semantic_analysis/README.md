# Neo4j Cypher Semantic Error Analysis

## Overview

This analysis examines 13,774 converted (question, Cypher, TypeQL) triples across 22 databases to identify cases where the **original Cypher query is semantically wrong** but the **TypeQL conversion is correct** — specifically because TypeDB's schema model, role-based relations, and validation caught errors that Cypher's looser structure allowed through.

The TypeQL queries were validated against a running TypeDB instance during conversion. The Cypher queries were generated by LLMs (GPT-4o, Claude Opus) from English questions against Neo4j schemas. This creates a natural experiment: both languages target the same question, but TypeDB's stricter type system and explicit relation semantics act as a correctness filter.

**Key finding**: 597 queries (4.3%) contain semantic errors in the Cypher that TypeDB's schema model prevented or corrected in the TypeQL. An additional 640 queries have simpler Cypher generation issues (missing aggregations, thresholds, etc.) that are attributable to LLM generation quality rather than language-level differences.

## Semantic Errors Caught by TypeDB

These are cases where TypeDB's language design — not just better prompting — produced a more correct query. Each category represents a structural advantage of TypeDB's type system over Cypher's pattern-matching model.

### 1. Relationship Direction Errors (198 queries)

**File**: `01_direction_errors.csv`

**The problem**: Cypher represents relationships with arrows (`->`, `<-`) whose direction is a syntactic convention detached from semantic meaning. An LLM can easily reverse `(a)-[:FOLLOWS]->(b)` vs `(a)<-[:FOLLOWS]-(b)` because nothing in the query text explains which end is the source.

**How TypeDB prevents this**: TypeQL uses named roles — `follows (follower: $a, followed: $b)` — where the role names carry the semantics. The schema defines which entity types can play which roles, so a direction error becomes a type error caught at validation time.

**Typical example** (companies):

```
Question: "List the top 3 people who are investors in more than one organization."

Cypher (WRONG):    (p:Person)-[:HAS_INVESTOR]->(o:Organization)
                   ← arrow says Person points to Organization via HAS_INVESTOR,
                     but schema says Organization-[:HAS_INVESTOR]->Person

TypeQL (CORRECT):  (investor: $p, organization: $o) isa invested_in;
                   ← roles make it unambiguous: the person IS the investor
```

**Most affected databases**: companies (71 queries across both sources), twitch (60), fincen (21), neoflix (16), twitter (14).

The companies schema is particularly susceptible because relationship names like `HAS_CEO`, `HAS_INVESTOR`, `HAS_BOARD_MEMBER` are ambiguous about direction — does the organization "have" an investor, or does the investor "have" an organization? The Neo4j schema convention (Organization)-[:HAS_INVESTOR]->(Person) is counterintuitive enough that LLMs consistently get it backwards. TypeDB's role names (`investor: $p, organization: $o`) eliminate this ambiguity entirely.

### 2. Relation Counting vs Property Shortcutting (180 queries)

**File**: `02_relation_counting_errors.csv`

**The problem**: When a question asks "how many times was X retweeted" or "which movies have the most reviews", Cypher allows two approaches: (a) count the actual relationships, or (b) read a denormalized property like `t.favorites`. LLMs frequently choose (b) even when the property measures something different.

**How TypeDB prevents this**: TypeQL has no denormalized property shortcut for relationship counts. To answer "how many retweets", you must traverse the `retweets` relation and count it explicitly. This forces the correct semantics.

**Typical example** (twitter — favorites/retweets confusion):

```
Question: "Which three tweets have the highest retweet counts?"

Cypher (WRONG):    RETURN t.text, t.favorites ORDER BY t.favorites DESC
                   ← returns favorite count instead of retweet count

TypeQL (CORRECT):  retweets (original_tweet: $t, retweeting_tweet: $rt);
                   reduce $count = count($rt) groupby $t;
                   ← explicitly counts retweet relations
```

This pattern appears 12 times in Twitter alone (both synthetic-1 and synthetic-2), always with the same error: Cypher uses `t.favorites` where the question asks about retweets.

**Other subtypes of this error**:
- **Northwind**: Cypher reads `o.discount` from the Order node, but discount is a property of the ORDERS *relationship* (the junction between Order and Product). TypeQL models this as `$rel isa orders (order: $o, product: $p); $rel has discount $d;` — the relation-as-entity pattern makes the ownership clear.
- **Movies**: Cypher uses `size(r.roles)` or `size(collect(distinct r.roles))` which is fragile pattern comprehension. TypeQL counts distinct `roles` attribute instances on the `acted_in` relation directly.
- **Fincen**: Cypher uses self-referencing patterns like `(e)-[:ORIGINATOR]->(f:Filing)-[:ORIGINATOR]->(e)` that don't match the schema. TypeQL's explicit `originator (originating_entity: $e, filing: $f)` avoids this.

**Note**: Some entries in the companies dataset (indices around 537, 564, 642, 646) show TypeQL queries unrelated to the English question — these are residual CSV corruption from an earlier processing stage and should be disregarded.

### 3. Property Ownership Errors (160 queries)

**File**: `03_property_misattribution.csv`

**The problem**: Cypher's property access (`node.property`) has no compile-time validation — accessing a non-existent property silently returns null. LLMs exploit this looseness by guessing property names based on context rather than checking the schema.

**How TypeDB prevents this**: TypeQL's `has` and fetch patterns are validated against the schema at query time. If entity type X doesn't own attribute Y, the query fails with a type error.

**Typical examples**:

- **Twitch**: `s.name` on Stream — the schema defines `stream_name` on Stream, not `name`. The LLM assumed the property name based on common patterns. (28 queries)
- **Movies (s2)**: `p.roles` on Person — `roles` is an attribute of the `acted_in` relation, not the Person entity. TypeQL: `$ai isa acted_in (actor: $p); $ai has roles $r;` (46 queries)
- **Northwind**: `o.discount` on Order — `discount` belongs to the `orders` relationship (junction entity), not the Order node. (29 queries)
- **Neoflix**: `p.job` on Person — the schema has no `job` attribute on Person. TypeQL uses the relation type itself (e.g., `crew_for`) to distinguish roles. (13 queries)

### 4. Hallucinated Relationship Types (28 queries)

**File**: `04_hallucinated_relationships.csv`

**The problem**: LLMs invent relationship types that don't exist in the schema, based on world knowledge rather than the actual data model.

**How TypeDB prevents this**: TypeQL requires all relation types to be defined in the schema. A query referencing a non-existent relation fails at parse/validation time.

**Examples** (all from companies):
- `[:AUTHOR]` — doesn't exist; the schema has `MENTIONS` between Articles and Organizations
- `[:HAS_AUTHORED]` — hallucinated along with node types `Book` and `Category`
- `[:FILED]` — doesn't exist in fincen schema; the correct relation is `filed`/`originator`

### 5. Hallucinated Properties (19 queries)

**File**: `05_hallucinated_properties.csv`

**The problem**: LLMs invent properties that don't exist on the referenced node type, based on common sense rather than the schema.

**Examples**:
- `c.population` on City — the companies schema has no population data for cities (8 queries)
- `o.foundingDate` on Organization — this property doesn't exist; the schema has `isDissolved`, `isPublic`, etc. (4 queries)
- `o.nbrPatents` on Organization — hallucinated entirely (2 queries)
- `t.retweets` on Tweet — the retweet count isn't a property; it requires counting the `retweets` relation (1 query)

### 6. Hallucinated Node Labels (12 queries)

**File**: `06_hallucinated_labels.csv`

**The problem**: LLMs reference node types that don't exist in the database schema.

**Examples**:
- `Book`, `Category` — hallucinated in companies schema (which has Article, IndustryCategory)
- `Acted` — hallucinated in recommendations (the relationship is `ACTED_IN`, not a node type)
- `Language` — referenced in movies but doesn't exist as a node label in the s2 schema

## Assessment

### Why These Errors Matter

These are not random LLM mistakes — they reveal systematic weaknesses in Cypher's design that TypeDB's type system addresses:

1. **Direction errors (34% of semantic issues)**: Cypher's arrow syntax is a poor carrier of semantic information. When relationship names are ambiguous (e.g., `HAS_INVESTOR` — who "has" whom?), LLMs guess wrong at the same rate a human would. TypeDB's role names eliminate guessing.

2. **Counting errors (30%)**: Cypher's ability to access denormalized properties creates an attractive nuisance — LLMs take the shortcut of reading `.favorites` instead of counting `RETWEETS` relationships because the property access is syntactically simpler. TypeDB doesn't offer this shortcut, so the query must be semantically correct.

3. **Property errors (27%)**: Cypher's null-on-missing-property behavior means schema violations are silent. TypeDB's ownership model turns them into hard errors, forcing correct attribute placement.

4. **Hallucination errors (10%)**: Cypher will happily execute a query against non-existent labels, relationships, or properties — returning empty results. TypeDB rejects these at query validation time.

## Methodology

Scanner: `pipeline/scripts/cypher_review_scan.py`

The scanner operates in 4 layers:
1. **Question vs Cypher structural checks**: Pattern-matches English questions for aggregation/sorting/negation keywords and verifies their presence in Cypher
2. **Question vs Cypher semantic checks**: Verifies the returned entity type matches the question's subject
3. **Neo4j schema validation**: Checks Cypher against `neo4j_schema.json` for valid labels, relationship types, properties, and directions
4. **TypeQL cross-reference**: Compares structural features of the validated TypeQL against the Cypher to find discrepancies

Confidence levels: `high` (structural mismatch with schema or clear keyword absence), `medium` (heuristic pattern match), `low` (speculative). Only high and medium are included in the "other issues" file.

## CSV Format

All CSV files share the same columns:

| Column | Description |
|--------|-------------|
| `source` | Source dataset (`synthetic-1` or `synthetic-2`) |
| `database` | Database name (e.g., `twitter`, `companies`) |
| `original_index` | Query index in the source dataset |
| `confidence` | Flag confidence: `high`, `medium`, or `low` |
| `check` | Scanner check name that flagged this query |
| `detail` | Human-readable description of the issue |
| `question` | English question |
| `cypher` | Original Cypher query (may be truncated to 500 chars) |
| `typeql` | Validated TypeQL query (may be truncated to 500 chars) |

Rows are sorted by `source`, then `database`, then `original_index`.
